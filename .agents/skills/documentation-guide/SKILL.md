# ドキュメント執筆・保守ガイドライン

ドキュメント体系の整合性，鮮度，可読性を維持するための執筆・保守ルール．ドキュメント変更時のブランチ運用，ワークツリー管理，コミット・PR 手順は `dev-workflow` スキルに従う．

## 1. ドキュメント体系と責務分離

| 階層 / ディレクトリ | 言語 | 役割・責務 | 含まないもの (委ねる先) |
| :--- | :--- | :--- | :--- |
| **ルート** ([README.md](../../../README.md), [README.ja.md](../../../README.ja.md)) | 英 / 日 (同期) | リポジトリ概要，Tech Stack，全体構成，クイックスタート | 詳細な手順や各ホストの深掘り (`docs/`, `hosts/`) |
| **`docs/`** | 日本語 | システム横断の基本設計仕様，運用手順，ハードウェア解説，障害復旧，調査ノート | コードそのものの実装 |
| **各サブディレクトリ** (`hosts/*/`, `nixos/*/` 等) | 英語 | 当該ディレクトリのコード索引，モジュール一覧，ハードウェア諸元 | 長大な運用手順・システム横断の設計 (`docs/`) |
| **エージェント運用** ([AGENTS.md](../../../AGENTS.md), [GEMINI.md](../../../GEMINI.md), [TODO.md](../../../TODO.md)) | 日本語 | エージェントの行動規範，ツール運用制約，実装進捗 | システムの詳細な技術仕様 (`docs/`) |
| **`.agents/skills/`** | 日 / 英 | エージェントが実行する作業手順・ノウハウ | システム全体の恒久的なドキュメント (`docs/`) |

## 2. 文体・スタイル規則

### 日本語文書 (`docs/`, [README.ja.md](../../../README.ja.md), [AGENTS.md](../../../AGENTS.md) 等)
- 句読点には全角カンマ `，` と全角ピリオド `．` を使用する (pre-commit フックが和文の読点・句点を自動置換する)．
- 文体は技術文書として簡潔かつ論理的な常体 (「〜である」「〜する」) を基本とする．
- 機械翻訳調や不自然な主述関係，不必要な重複表現を排し，要点を明確に記述する．
- 視認性を重視し，比較や属性一覧はテーブル，手順は番号付きリストを使用する．
- ネットワーク構成や処理フローは Mermaid ダイアグラムを使用する．

### 表記統一ルール (括弧・カンマ・英語原語)

丸括弧は半角 `()` に統一し，全角括弧は使用しない．

カンマは用途で使い分ける．

| 用途 | 記号 | 例 |
| :--- | :--- | :--- |
| 日本語の読点，語句・文節の区切り | 全角 `，` | 設定を変更し，検証する． |
| 非日本語 (英数字，コード，技術用語，パラメータ，識別子) の列挙 | 半角 `,` | `AMD, NVIDIA, Intel`, `x86_64-linux, aarch64-linux`, `1.80 GHz, 4.60 GHz` |

日本語だけで意味が通じる語の直後に，英語原語をカッコ併記しない．

| 併記しない | 推奨 |
| :--- | :--- |
| `セキュリティ境界 (Security Boundary)` | セキュリティ境界 |
| `優先度制御 (Priority System)` | 優先度制御 |
| `切り戻し (Failback)` | 切り戻し |
| `帯域外管理 (Out-of-Band Management)` | 帯域外管理 |
| `短期証明書 (Short-lived Certificate)` | 短期証明書 |

略称 (SSOT, TTY, GRUB, DR 等)，プロトコル名，規格名，固有名詞は併記してよい．

### 英語文書 ([README.md](../../../README.md), サブディレクトリ README)
- 簡潔で客観的な技術英語 (Plain Technical English, 命令文または叙述文) を基本とする．
- コードブロック，リスト，表を中心とし，冗長な説明文は削る．

### コード内コメント (`hush` 規約)
- 原則として英語で記述する．
- `hush` スキル (`~/.agents/skills/hush/`) に従い，自明な解説やコードの言い換えコメントは書かず，名前で意図を表現する．
- コードのみでは意図を読み取れない場合のみ，背景や理由を 1〜2 行で記述する．

## 3. LLM 的文章の排除とリライト規則

LLM 生成文章に多い空虚な美辞麗句，不要な前置き・結び，冗長な述語を排除するための規則．

### ゼロ前置き・ゼロ後置き
- 「本ドキュメントでは〜について解説します」「以下に〜を示します」「In this document, we delve into...」等の導入文・メタ解説を書かず，先頭から事実，定義，表，コマンド，設定例を直接記述する．
- 「以上の手順によりシームレスに連携できます」「By following this guide, you will achieve...」等の美辞麗句・感想・まとめを排し，技術仕様と手順の記述のみで完結させる．

### 禁止ワード対照表

| 言語 | 禁止ワード / 表現 | 推奨される代替表現 / 指針 |
| :--- | :--- | :--- |
| **英語** | *delve (into)* | *inspect, examine, read, see*，または直接対象を記述 |
| **英語** | *testament to* | *shows, demonstrates*，または削除 |
| **英語** | *tapestry* | 具体的なアーキテクチャ・構成要素名を明記 |
| **英語** | *robust* | *fault-tolerant, resilient, reliable*，または具体的な耐性仕様を記述 |
| **英語** | *seamless / seamlessly* | *direct, automatic, unified*，または具体的な連携動作を記述 |
| **英語** | *streamline* | *simplify, automate, organize* |
| **英語** | *leverage* | *use, apply* |
| **英語** | *crucial / paramount / vital* | *required, necessary*，または直接制約条件を記述 |
| **英語** | *comprehensive* | *complete, full, end-to-end*，または対象範囲を具体化 |
| **英語** | *foster / cultivate* | *enable, support* |
| **英語** | *plethora / myriad* | *many, multiple*，または具体数を記述 |
| **日本語** | 「包括的な」「網羅的な」 | 具体的な範囲を明記，または「全〜」「一覧」 |
| **日本語** | 「堅牢な」「堅牢性」 | 具体的な障害耐性・冗長化・エラー処理の仕様を記述 |
| **日本語** | 「シームレスな」「シームレスに」 | 「透過的な」「自動的な」「単一の」「直接」 |
| **日本語** | 「〜を活用する」「〜をレバレッジする」 | 「〜を使用する」「〜を適用する」「〜を用いる」 |
| **日本語** | 「〜の実現」「〜を可能にする」 | 「〜する」「〜に対応する」 (動詞で直接表現) |
| **日本語** | 「〜を念頭に置く」「〜に留意する」 | 「〜を確認する」「〜を遵守する」「〜に注意する」 |
| **日本語** | 「非常に」「極めて」「極めて重要な」 | 削除，または「必須」「〜が必要」と断定 |
| **日本語** | 「看取する」「担保する」 | 「確認する」「保証する」 |
| **日本語** | 「企図する」「包摂する」 | 「意図する」「含む」 |
| **日本語** | 「〜に資する」「〜の敷設」 | 「役立つ」「導入する」「構築する」 |
| **日本語** | 「直叩き」「直結で叩く」 | 「D-Bus 経由で直接呼び出す」「直接リクエストする」 |
| **日本語** | 「正本」「土台」 | 「定義ファイル」「原本」「基盤」「共通設定」 |
| **日本語** | 「配線する」「引き回す」 | 「接続する」「設定する」「引き渡す」 |
| **日本語** | 「〜側に倒す」「素通りする」 | 「〜を採用する」「バイパスする」 |
| **日本語** | 「効く」「静かに動く」 | 「動作する」「適用される」「バックグラウンドで稼働する」 |
| **日本語** | 「〜を一手に担う」「〜という形になる」 | 「〜を管理する」「〜となる」「〜する」 |

### 冗長述語の圧縮

| 冗長な表現 | 圧縮後の表現 |
| :--- | :--- |
| 〜を行うことができる / 〜することが可能 | 〜できる / 〜する |
| 〜の実施を行う / 〜の実行を行う | 〜を実施する / 〜を実行する / 〜する |
| 〜の確認を行う | 〜を確認する |
| 〜という点に注意が必要である | 〜に注意する / 〜を避ける |
| 〜を目的として策定されている | 〜を目的とする / 〜のために規定する |
| 〜となっている / 〜となっています | 〜である / 〜する |

### Plain Technical Writing 原則
- 主観的な賞賛形容詞 (「優れた」「最適な」「洗練された」) を排除し，数値・仕様・挙動・制約を直接記述する．
- 曖昧な受動態や婉曲表現を避け，主語と動作を明確にする．
- コードの言い換えや自明な説明を削り，読者・エージェントが判断に必要とする基準と手順に絞る．

### 構文・修辞ルール

1. **架空の二項対立を書かない**:
   - 「Aであり，Bではない」「単にAだけでなくBでもある」「AというよりもBである」等の対比構文を避け，肯定文で技術的事実のみを記述する．
   - 否定節を使うのは，読者が誤認して設定ミスを招く具体的理由がある場合 (例: `nvidia-smi` ではなく sysfs を参照する) に限る．
2. **接続詞を機械的に挟まない**:
   - 「さらに」「また」「このように」「具体的には」などの接続詞を並べず，文の配置順序で論理を伝える．
3. **主述を復元し，直訳・比喩表現を排除する**:
   - 非生物を主語にした比喩動詞 (「静かに壊れる」「正本」「土台」「〜側に倒す」等) を避け，「誰が／何が，何をどうするか」を直接記述する．
4. **検証可能トークン (パス・オプション・コマンド) を明示する**:
   - 抽象的な形容詞や説明文を排し，ファイルパス，Nix オプション名，systemd ユニット名，CLI コマンド，数値などの検証可能トークンを直接記述する．
5. **箇条書きの擬似見出しを解体する (Label-itis)**:
   - `- **見出し**: 本文` の形は，見出しと本文で同じ内容を二重に読ませ，主述関係を分断する．各項目はラベルに依存せず，一息で読める自立した文にする．
   - 属性・設定値・分類・対応関係の列挙はテーブルに，時系列の手順は番号付きリストに変換する．詳細な解説は箇条書きの入れ子ではなく `###` サブセクションまたは段落に昇格させる．短いキー (設定項目名など) だけの定義リスト的な箇条書きは許容する．
   - 改善例:
     - タスク・TODO: × `- **キャッシュサーバーの導入 (Attic 等)**: ホスト間でビルドキャッシュを共有する．` → ◯ `- Attic 等のキャッシュサーバーを導入し，ホスト間でビルドキャッシュを共有する．`
     - 設計・運用原則: × `- **タイマーポーリング禁止**: コマンドやプロセスの完了待ちに schedule による小刻みなタイマー監視を行わない．` → ◯ `- コマンドやプロセスの完了待ちに schedule による小刻みなタイマー監視を行わず，完了通知を待機する．`
     - 分類・対応関係: × `- **全ホスト共通ツール**: nixos/environment/ に配置する．` → ◯ `| 全ホスト共通ツール | nixos/environment/ |` の表に置き換える．
6. **太字の過剰装飾を抑制する**:
   - マークアップに頼らないと読みにくい文章は，主述関係や論理構造が不十分な証拠である．文の構造，語順，見出しの階層で要点を伝える．
   - 太字は表のヘッダー，定義リストのキー，重大な警告 (データ破壊や文鎮化リスク) に絞り，散文・段落内では原則として使用しない．

### 推敲チェックリスト

- [ ] 文頭・文末に前置きや感想 (「ここでは〜を解説します」「〜が可能になります」等) がない．
- [ ] 第 2 節の表記統一ルール (半角 `()`，全角 `，` と半角 `,` の区分，英語原語の併記禁止) に従っている．
- [ ] `- **題**: 詳細` の擬似見出し (Label-itis) を解体し，自立した文，表，番号付きリスト，サブセクションに再編している．
- [ ] 散文・段落内の過剰な太字 (`**強調**`) を削り，文章構造そのもので読めるようにしている．
- [ ] 架空の二項対立 (「Aであり，Bではない」) の否定節を削り，事実のみを記述している．
- [ ] 不要な接続詞 (さらに，また，このように等) を削り，文の順序で論理を伝えている．
- [ ] 禁止ワード対照表の語彙 (包括的，堅牢，シームレス，看取，担保，活用 等) が残っていない．
- [ ] 曖昧な賞賛形容詞を排し，技術的事実・機構・数値を記述している．
- [ ] 冗長な述語 (〜を行う，〜することが可能である) を直接の動詞に圧縮している．
- [ ] 英語は簡潔な Plain Technical English (能動態・命令文中心) になっている．

## 4. ドキュメント種別の標準テンプレート

ドキュメントは種別ごとの標準構成と見出し階層に従って執筆する．プレースホルダは，コマンドやパスなど値を埋めるものを英語 (`<hostname>`, `<command>`)，記述内容を表すものを日本語 (`<フェーズ名>`, `<仕様>`) で書く．

### 4.1 運用手順書 (`docs/operations/`)

システムの追加，鍵管理，バックアップ，プロビジョニング，フェイルオーバーなど，定常時と障害時の運用手順を記述する．標準構成は次のとおり．

1. タイトル
2. 前提条件 (対象ホスト，実行権限，必要ツール，作業前チェックリスト)
3. ステップ別手順 (`### Step 1:` 形式で見出しを統一)
4. 事後検証と期待される出力
5. 関連ドキュメント

````markdown
# <運用手順書タイトル>

<対象，目的，実行契機を 1〜2 文で記述する．>

## 1. 前提条件

| 項目 | 要件・確認事項 |
| :--- | :--- |
| 対象ホスト | `<hostname>` |
| 実行権限 | 一般ユーザー / `sudo` / `root` |
| 必要ツール | `ssh`, `sops`, `age` |
| 前提状態 | トピックブランチ作成済み，開発シェル有効化 |

- [ ] 対象ホストへ疎通できる
- [ ] マスター鍵 `~/.config/sops/age/keys.txt` が配備されている

---

## 2. 作業手順

### Step 1: <フェーズ名>

```bash
<command>
```

### Step 2: <フェーズ名>

```bash
<command>
```

---

## 3. 事後検証

```bash
<verification-command>
```

期待される出力:

```text
<期待される出力>
```

---

## 関連ドキュメント
- [目次](../README.md) — リポジトリ内全ドキュメントの索引
- [<関連設計書>](../architecture/<filename>.md) — <説明>
````

### 4.2 ハードウェア固有ガイド (`docs/hardware/`)

1. タイトル
2. 概要 (対象ホスト，設計方針，物理制約)
3. 全体構成図 (Mermaid ダイアグラムで接続トポロジを示す)

### 4.3 トラブルシューティング (`docs/troubleshooting/`)

1. タイトル
2. 障害一覧表 (障害種別，主なエラー兆候，影響ホスト，初動対応)
3. 障害ごとに `## 1.` のセクションを設け，現象，原因，切り分け・復旧手順の 3 段構成にする
4. 関連ドキュメント

### 4.4 調査ノート (`docs/research/`)

実機検証，upstream コードの読解，アーキテクチャ調査，歴史的経緯を記録する．標準構成は次のとおり．

1. タイトル
2. 調査対象と環境 (対象ホスト，実機検証環境のバージョン，upstream の調査リビジョン)
3. 概要と結論 (問いと回答の表)
4. 分析 (`## 1.` と `### 1.1` の階層で構成し，コード引用，シーケンス図，API トレースを添える)
5. 関連ドキュメント (必要に応じ `## 出典` を追加)

````markdown
# <調査ノートタイトル>

<調査目的，対象アーキテクチャ，スコープを記述する．>

| 項目 | 対象・バージョン |
````

### 4.5 サブディレクトリ README (`nixos/*/`, `home/*/` 等)

モジュールやプロファイルの索引として，各ファイルの役割，オプション，主要コマンドを英語で記述する．標準構成は次のとおり．

1. タイトル (`# <Directory Name>` にパスを併記)
2. ディレクトリの責務 (1〜2 文)
3. モジュール一覧 (`| File | Description | Options / Notes |`)
4. 主要コマンド (任意)
5. `## References`

## 5. 参照セクションの標準記法

ドキュメントとコードの相互参照の書式を統一し，リンク切れを防ぐ．

### 日本語文書 (`docs/` 配下)
- 見出しは必ず `## 関連ドキュメント` とする．
- リスト項目は `- [タイトル](相対パス) — 説明` の形式で統一する (全角ダッシュ `—` で区切る)．
- 相対パスは，現在のファイルからの正確なパスを記述する．

```markdown
## 関連ドキュメント
- [目次](../README.md) — ドキュメント全体の索引
- [ネットワーク設計](../architecture/network-topology.md) — Nebula メッシュネットワークと IP 体系
- [新ホスト追加手順](adding-a-host.md) — 新規ホストの登録と初期プロビジョニング手順
```

### 英語文書 (サブディレクトリ README 等)
- 見出しは必ず `## References` とする．
- リスト項目は `- 説明: [リポジトリルートからのパス](相対リンク)` の形式で統一する．

```markdown
## References

- System architecture overview: [docs/architecture/overview.md](../../docs/architecture/overview.md)
- Hardware tuning guide: [docs/hardware/thinkpad-x1c7.md](../../docs/hardware/thinkpad-x1c7.md)
- User-level module configuration: [home/desktop/](../../home/desktop/README.md)
```

## 6. 情報の重複排除と一元化

1. 同一の手順 (新ホスト追加，SOPS 鍵登録，private flake input のブートストラップ等) を複数の README やスキルに重複して書かない．手順詳細は `docs/operations/` 配下にまとめ，他のドキュメントからはリンクを張る．
2. 各コードディレクトリの README は，当該ディレクトリ固有の仕様・オプション一覧・主要コマンドに絞る．ハードウェアのチューニングやトラブルシューティングは `docs/hardware/` や `docs/troubleshooting/` に委ねる．

## 8. ドキュメントレビューと改善

ドキュメントの新規作成や大幅な改修時は，技術的整合性と文章品質を確認する (外部ワーカーへの技術検証委譲やサブエージェントによる文章推敲は [GEMINI.md](../../../GEMINI.md) と `coding-worker` スキルを参照)．コミット・PR 手順は `dev-workflow` スキルに従う．

### 技術的整合性の検証観点
手順書・設計書に記載された技術仕様，シェルコマンド，systemd ユニット名，Nix 設定値，ネットワーク構成について以下を確認する:
- 記載されたコマンドが実際のホスト環境・NixOS 仕様に合致しているか．
- 参照されているファイルパスやサービス名がリポジトリ内のコードと整合しているか．
- 復旧手順や運用手順書に手順抜けやエッジケースがないか．

### 文章品質・整合性・コメント (`hush`) の検証観点
ドキュメントの文章，章立て，相互参照，コード内コメントについて以下を確認する:
- 第 4 節の標準テンプレート (構成，見出し階層，表ヘッダー) に準拠しているか．
- 第 5 節の参照セクション記法に準拠しているか．
- 第 2 節の表記統一ルール (半角 `()`，全角 `，` と半角 `,` の区分，英語原語の併記禁止) に従っているか．
- 第 3 節のリライト規則に従い，前置き・結びの排除，擬似見出しの解体 (Label-itis)，禁止ワードの不使用，冗長述語の圧縮が行われているか．
- 他ドキュメントとの不要な重複がなく，基準となる `docs/` を参照しているか．
- 相対リンクおよびアンカーが正しく機能しているか (リンク切れがないか)．
- コード内コメントが `hush` スキル (`~/.agents/skills/hush/`) に従っているか (自明な解説がなく，名前で意図を表現できているか)．
