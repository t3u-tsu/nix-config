# ドキュメント執筆・保守ガイドライン

執筆・保守の規則と，機械検証で判定できない判断基準を定める．ブランチ運用・コミット・PR は `dev-workflow` スキル，個別ファイルの配置と索引は [docs/README.md](../../../docs/README.md) を唯一の情報源とする．

## 1. 責務分離

| 対象 | 言語 | 役割 | 含めない内容 |
| :--- | :--- | :--- | :--- |
| ルート [README.md](../../../README.md) / [README.ja.md](../../../README.ja.md) | 英 / 日 (常に同期) | 概要，Tech Stack，全体構成，クイックスタート | 詳細手順，ホスト別の深掘り |
| [docs/](../../../docs/README.md) | 日本語 | システム横断の設計仕様，運用手順，ハードウェア解説，障害復旧，調査ノート | 実装コード |
| コードディレクトリの `README.md` (`hosts/*/`, `nixos/*/`, `home/*/`) | 英語 | 当該ディレクトリの索引，モジュール一覧，ハードウェア諸元，主要コマンド | 長大な運用手順，システム横断の設計 |
| [AGENTS.md](../../../AGENTS.md)，[GEMINI.md](../../../GEMINI.md)，[TODO.md](../../../TODO.md) | 日本語 | エージェントの行動規範，ツール運用制約，実装進捗 | 技術仕様 |
| `.agents/skills/` | 日 / 英 | エージェントが実行する作業手順・ノウハウ | 恒久的なシステム仕様 |

同一の手順を複数箇所に書かない．新ホスト追加，SOPS 鍵登録，private flake input のブートストラップ等は `docs/operations/` に置き，他のドキュメントからはリンクする．

## 2. 表記規則

- 丸括弧は半角 `()` のみとし，全角 `（）` を使用しない．
- 句読点は全角 `，` と `．` を使う．pre-commit の `ja-punctuation` が和文の読点・句点を自動置換する．
- 文体は常体 (「〜である」「〜する」)．属性・比較はテーブル，手順は番号付きリスト，ネットワーク構成や処理フローは Mermaid で示す．
- 英語文書は Plain Technical English (能動態・命令文) で書き，コードブロック，リスト，表を中心に構成する．
- コード内コメントは英語で書き，`hush` スキル (`~/.agents/skills/hush/`) に従って自明な解説を排し，名前で意図を表現する．

カンマは用途で使い分ける．

| 用途 | 記号 | 例 |
| :--- | :--- | :--- |
| 日本語の読点，語句・文節の区切り | 全角 `，` | 設定を変更し，検証する． |
| 非日本語 (英数字，コード，技術用語，識別子) の列挙 | 半角 `,` | `AMD, NVIDIA, Intel` / `1.80 GHz, 4.60 GHz` |

日本語で意味が通じる語の直後に英語原語を併記しない (× `セキュリティ境界 (Security Boundary)`，○ セキュリティ境界．同様に 優先度制御，切り戻し，帯域外管理，短期証明書)．略称 (SSOT, TTY, GRUB, DR 等)，プロトコル名，規格名，固有名詞は併記してよい．

## 3. LLM 的文章の排除

前置きと結びを書かない．「本ドキュメントでは〜を解説します」「以下に〜を示します」「以上の手順により〜できます」等の導入・メタ解説・感想を置かず，先頭から事実，定義，表，コマンド，設定例を書く．英語でも *In this document, we delve into...* や *By following this guide, you will...* を書かない．

禁止語彙の完全な一覧と検出は `scripts/check-docs.ysh` が担う．語を機械的に置換せず，次の方針で具体化する．

| 言語 | 禁止語 (推奨する代替) |
| :--- | :--- |
| 英語 | *delve* (inspect / examine) / *testament to* (shows) / *tapestry* (構成要素名) / *robust* (fault-tolerant / reliable または耐性仕様) / *seamless* (direct / automatic) / *streamline* (simplify / automate) / *leverage* (use) / *crucial*・*paramount*・*vital* (required) / *comprehensive* (complete / end-to-end) / *foster*・*cultivate* (enable / support) / *plethora*・*myriad* (many または具体数) |
| 日本語 | 堅牢 (障害耐性・冗長化・エラー処理の仕様) / 包括的・網羅的 (対象範囲の明示) / シームレス (透過的・自動的・直接) / 活用・レバレッジ (使用・適用) / 〜の実現・〜を可能にする (動詞で断定) / 念頭に置く・留意する (確認・遵守) / 非常に・極めて (削除または必須) / 看取・担保 (確認・保証) / 企図・包摂 (意図・含む) / 〜に資する・敷設 (役立つ・導入) / 直叩き (D-Bus 経由で直接呼び出す) / 正本・土台 (定義ファイル・原本・基盤) / 配線する・引き回す (接続・設定) / 側に倒す・素通り (採用・バイパス) / 効く・静かに動く (動作する・適用される) / 一手に担う・という形になる (管理する・となる) |

冗長な述語は動詞に圧縮する．

| 冗長な表現 | 圧縮後 |
| :--- | :--- |
| 〜を行うことができる / 〜することが可能 | 〜できる / 〜する |
| 〜の実施を行う / 〜の実行を行う / 〜の確認を行う | 〜を実施する / 〜を実行する / 〜を確認する |
| 〜という点に注意が必要である | 〜に注意する / 〜を避ける |
| 〜となっている / 〜を目的として策定されている | 〜である / 〜を目的とする |

構文・修辞の規則．

1. 架空の二項対立を書かない．「Aであり，Bではない」「単にAだけでなくBでもある」「AというよりもBである」を避け，肯定文で技術的事実を書く．否定節は，読者が誤認して設定ミスを招く場合 (例: `nvidia-smi` ではなく sysfs を参照する) に限る．
2. 接続詞を機械的に挟まない．「さらに」「また」「このように」「具体的には」を並べず，文の配置順序で論理を伝える．
3. 比喩動詞と非生物主語を避け，主述を復元する．「静かに壊れる」「土台」「側に倒す」等を使わず，何が何をするかを直接書く．
4. 検証可能トークンを書く．ファイルパス，Nix オプション名，systemd ユニット名，CLI コマンド，数値を示し，抽象的な形容詞で代替しない．
5. 箇条書きの擬似見出し (Label-itis) を解体する．`- **題**: 本文` は見出しと本文で同じ内容を二重に読ませる．属性・対応関係はテーブル，時系列は番号付きリスト，解説は `###` サブセクションか段落に昇格させ，短いキーの定義リストのみ許容する．
6. 太字を過剰に使わない．表のヘッダー，定義リストのキー，重大な警告 (データ破壊・文鎮化) に絞り，散文・段落内では使わない．

## 4. 種別ごとの標準構成

プレースホルダは，コマンドやパスなど値を埋めるものを英語 (`<hostname>`, `<command>`)，記述内容を表すものを日本語 (`<フェーズ名>`, `<仕様>`) で書く．章見出しは `## <番号>. <章名>`，項は `### <番号>.<番号> <項名>` の階層に統一する．

| 種別 | 配置 | 必須セクション (この順) | 固有規約 |
| :--- | :--- | :--- | :--- |
| アーキテクチャ | `docs/architecture/` | タイトル / `## 1.` 以降の設計項目 / `## 関連ドキュメント` | トポロジは Mermaid，構成要素はテーブル，設定は `nix` フェンス |
| 運用手順書 | `docs/operations/` | タイトル / 前提条件 (対象ホスト・実行権限・必要ツール・作業前チェックリスト) / 作業手順 / 事後検証 (コマンドと期待出力) / `## 関連ドキュメント` | 手順の章見出しは `### Step <番号>: <フェーズ名>`，コマンドは `bash` フェンスに実値を書く |
| ハードウェア固有 | `docs/hardware/` | タイトル / 諸元表 (対象ホスト・CPU・GPU・RAM・ストレージ) / トポロジ / チューニング項目 / `## 関連ドキュメント` | 各項目に背景と対象ホスト，`nix` 設定例，確認コマンドを添える |
| トラブルシューティング | `docs/troubleshooting/` | タイトル / 障害一覧表 (障害種別・エラー兆候・影響ホスト・初動対応) / 障害ごとの `## <番号>.` / `## 関連ドキュメント` | 各障害は 現象 (`text` フェンスにエラー原文) → 原因 → 切り分け・復旧手順 (`#### 対策 <番号>: <対策名>`) の 3 段構成 |
| 調査ノート | `docs/research/` | タイトル / 調査環境表 (対象ホスト・検証環境・upstream リビジョン) / 概要と結論 (問いと回答の表) / 分析 / `## 関連ドキュメント` | 分析は `## <番号>.` と `### <番号>.<番号>` の 2 階層とし，コード引用とシーケンス図を添える．出典は末尾の `## 出典` に置く |
| ホスト README | `hosts/<hostname>/README.md` | タイトル / Hardware Specifications / Configuration Summary / Host Services & Modules / Quick Operations / `## References` | [hosts/_template/README.md](../../../hosts/_template/README.md) を雛形にする．本文は英語 |
| モジュール README | `nixos/*/`, `home/*/` 等 | タイトル `# <Name> (<path/>)` / 責務 1〜2 文 / `## Modules` / 任意の `## Quick Operations` / `## References` | モジュール表は File / Description / Options の 3 列とし，有効化オプションと注記を書く．本文は英語 |

日本語ドキュメントの共通骨子．種別固有の章は `## 1.` 以降に置き，参照セクションを常に末尾に固定する．

````markdown
# <タイトル>

<対象，目的，実行契機を 1〜2 文で書く．>

| 項目 | 要件・確認事項 |
| :--- | :--- |
| 対象ホスト | `<hostname>` |

---

## 1. <章名>

### 1.1 <項名>

```bash
<command>
```

---

## 関連ドキュメント
- [目次](../README.md) — 全ドキュメントの索引
- [<関連設計書>](../architecture/<filename>.md) — <説明>
````

## 5. 参照セクション

日本語文書は `## 関連ドキュメント`，英語文書は `## References` で終える．相対パスは現在のファイルからの正確な位置を書き，全角ダッシュ `—` の後に 1 行の説明を添える．英語文書の記法は次のとおり．

```markdown
## References

- System architecture: [docs/architecture/overview.md](../../docs/architecture/overview.md)
- Host runbook: [docs/operations/adding-a-host.md](../../docs/operations/adding-a-host.md)
```

## 6. 配置と索引

新規ドキュメントの配置先，既存ドキュメントの一覧，各ファイルの責務は [docs/README.md](../../../docs/README.md) を唯一の情報源とし，本スキルに複製しない．追加・分割・削除・改名した場合は同じ PR で `docs/README.md` を更新する．

## 7. 検証

変更後に次を実行し，違反ゼロを確認する．

```bash
python3 scripts/check-markdown-links.py
ysh scripts/check-docs.ysh
```

`check-docs.ysh` は全角括弧，和文に隣接する半角カンマ，禁止語彙，擬似見出しの箇条書きを検出する．同スクリプトが判定しない項目を目視で確認する．

- [ ] 文頭・文末に前置き，メタ解説，感想，結びがない．
- [ ] 半角 `()`，全角 `，` `．`，非日本語列挙の半角 `,` を使い分けている．
- [ ] 英語原語の併記，擬似見出し，過剰な太字，架空の二項対立，不要な接続詞が残っていない．
- [ ] 冗長述語を動詞に圧縮している．
- [ ] 章立てが第 4 節の標準構成に一致し，参照セクションが第 5 節の記法に従っている．
- [ ] 手順・パス・コマンド・サービス名・Nix 設定値がリポジトリ内のコードと一致し，手順抜けやエッジケースがない．
- [ ] 他ドキュメントと重複せず，基準となる `docs/` を参照している．
- [ ] コード内コメントが `hush` 規約 (英語，名前で意図を表現) に従っている．
