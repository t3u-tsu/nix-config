# ドキュメント執筆・保守ガイドライン

ドキュメント体系の整合性，鮮度，可読性を維持するための執筆・保守ルール．ドキュメント変更時のブランチ運用，ワークツリー管理，コミット・PR 手順は `dev-workflow` スキルに従う．

## 1. ドキュメント体系と責務分離

| 階層 / ディレクトリ | 言語 | 役割・責務 | 含まないもの（委ねる先） |
| :--- | :--- | :--- | :--- |
| **ルート** (`README.md`, `README.ja.md`) | 英 / 日 (同期) | リポジトリ概要，Tech Stack，全体構成，クイックスタート | 詳細な手順や各ホストの深掘り (`docs/`, `hosts/`) |
| **`docs/`** | 日本語 | システム横断の基本設計仕様，運用手順，ハードウェア解説，障害復旧 | コードそのものの実装 |
| **各サブディレクトリ** (`hosts/*/`, `nixos/*/` 等) | 英語 | 当該ディレクトリのコード索引，モジュール一覧，ハードウェア諸元 | 長大な運用手順・システム横断の設計 (`docs/`) |
| **エージェント運用** (`AGENTS.md`, `GEMINI.md`, `TODO.md`) | 日本語 | エージェントの行動規範，ツール運用制約，実装進捗 | システムの詳細な技術仕様 (`docs/`) |
| **`.agents/skills/`** | 日 / 英 | エージェントが実行する作業手順・ノウハウ | システム全体の恒久的なドキュメント (`docs/`) |

## 2. 文体・スタイル規則

### 日本語文書 (`docs/`, `README.ja.md`, `AGENTS.md` 等)
- **句読点**: 必ず `，．` を使用する（全角の読点・句点はコミット時に pre-commit フックで `，．` に自動置換される）．
- **文体**: 技術文書として簡潔かつ論理的な常体（「〜である」「〜する」）を基本とする．
- **自然な日本語**: 機械翻訳調や不自然な主述関係，不必要な重複表現を排し，要点を明確に記述する．
- **箇条書き・表**: 視認性を重視し，比較や属性一覧はテーブル，手順は番号付きリストを使用する．
- **図解**: ネットワーク構成や処理フローは Mermaid ダイアグラムを使用する．

### 英語文書 (`README.md`, サブディレクトリ README)
- **文体**: 簡潔で客観的な技術英語（Plain Technical English，命令文または叙述文）．
- **過度な装飾の排除**: コードブロック，リスト，表を中心とし，冗長な説明文は削る．

### コード内コメント (`hush` 規約)
- 原則として英語で記述する．
- `hush` スキル（`~/.agents/skills/hush/`）に従い，自明な解説やコードの言い換えコメントは書かず，名前で意図を表現する．
- コードのみでは意図を読み取れない場合のみ，背景や理由を 1〜2 行で記述する．

## 3. LLM 文章脱却チェックリスト＆リライトルール（日・英対応）

LLM 生成文章特有の空虚な美辞麗句，不要な前置き・結び，冗長な述語を排除し，密度の高い技術文章を作成・維持するための規則．

### ゼロ前置き・ゼロ後置きの原則（Zero Preamble & Zero Postamble）
- **前置きの排除**: 「本ドキュメントでは〜について解説します」「以下に〜を示します」「In this document, we delve into...」「Here is a breakdown of...」等の導入文・メタ解説を書かず，先頭から事実，定義，表，コマンド，設定例を直接記述する．
- **結びの感想排除**: 「〜により堅牢な運用が可能になります」「以上の手順によりシームレスに連携できます」「By following this guide, you will achieve...」等の美辞麗句・まとめを排し，必要な技術仕様や手順の記述のみで完結させる．

### 禁止ワード対照表（日英対応）

| 言語 | 禁止ワード / 表現 | 推奨される代替表現 / 指針 |
| :--- | :--- | :--- |
| **英語** | *delve (into)* | *inspect, examine, read, see*，または直接対象を記述 |
| **英語** | *testament to* | *shows, demonstrates*，または削除 |
| **英語** | *tapestry* | 具体的なアーキテクチャ・構成要素名を明記 |
| **英語** | *robust* | *fault-tolerant, resilient, reliable*，または具体的な耐性仕様を記述 |
| **英語** | *seamless / seamlessly* | *direct, automatic, unified*，または具体的な連携動作を記述 |
| **英語** | *streamline* | *simplify, automate, organize* |
| **英語** | *leverage* | *use, apply* |
| **英語** | *crucial / paramount / vital* | *required, necessary*，または直接制約条件を記述 |
| **英語** | *comprehensive* | *complete, full, end-to-end*，または対象範囲を具体化 |
| **英語** | *foster / cultivate* | *enable, support* |
| **英語** | *plethora / myriad* | *many, multiple*，または具体数を記述 |
| **日本語** | 「包括的な」「網羅的な」 | 具体的な範囲を明記，または「全〜」「一覧」 |
| **日本語** | 「堅牢な」「堅牢性」 | 具体的な障害耐性・冗長化・エラー処理の仕様を記述 |
| **日本語** | 「シームレスな」「シームレスに」 | 「透過的な」「自動的な」「単一の」「直接」 |
| **日本語** | 「〜を活用する」「〜をレバレッジする」 | 「〜を使用する」「〜を適用する」「〜を用いる」 |
| **日本語** | 「〜の実現」「〜を可能にする」 | 「〜する」「〜に対応する」（動詞で直接表現） |
| **日本語** | 「〜を念頭に置く」「〜に留意する」 | 「〜を確認する」「〜を遵守する」「〜に注意する」 |
| **日本語** | 「非常に」「極めて」「極めて重要な」 | 削除，または「必須」「〜が必要」と断定 |
| **日本語** | 「〜の一助となる」「〜に役立つ」 | 削除，または具体的な機能仕様を客観記述 |

### 冗長述語の圧縮ルール（述語の直接化）

| 冗長な表現 | 圧縮後の表現 |
| :--- | :--- |
| 〜を行うことができる / 〜することが可能 | 〜できる / 〜する |
| 〜の実施を行う / 〜の実行を行う | 〜を実施する / 〜を実行する / 〜する |
| 〜の確認を行う | 〜を確認する |
| 〜という点に注意が必要である | 〜に注意する / 〜を避ける |
| 〜を目的として策定されている | 〜を目的とする / 〜のために規定する |
| 〜となっている / 〜となっています | 〜である / 〜する |

### Plain Technical Writing 原則
- **客観的・即物的記述**: 主観的な賞賛形容詞（「優れた」「最適な」「洗練された」）を排除し，数値・仕様・挙動・制約を直接記述する．
- **能動態・直接話法**: 曖昧な受動態や婉曲表現を避け，主語と動作を明確にする．
- **情報密度の最大化**: コードの言い換えや自明な説明を削り，読者・エージェントが必要とする具体的判断基準や手順に絞る．

### 構文・修辞ルールの指針（アンチAI構文の原則）

1. **二項対立構文（架空の対比項）の原則禁止**:
   - 「Aであり，Bではない」「単にAだけでなくBでもある」「AというよりもBである」等の対比構文を避ける．
   - 読者が実際に誤認してシステム障害や設定ミスを招く具体的理由（例: `nvidia-smi` ではなく sysfs を参照する）がある場合を除き，**否定節（〜ではない，単に〜だけでなく）を全削除し，肯定文で技術的事実のみを直接記述する**．
2. **論理標識（接続詞）の9割削減**:
   - 「さらに」「また」「このように」「具体的には」などの接続詞を機械的に挟まない．文の配置順序（論理構造）そのもので文脈を伝える．
3. **主述の復元と比喩カルクの排除**:
   - 非生物主語＋比喩動詞（「静かに壊れる」「正本」「土台」「〜側に倒す」等の英語翻訳カルク）を避け，「誰が／何が，何をどうするか」（主語＋能動動詞＋対象）を直接記述する．
4. **検証可能トークン（パス・オプション・コマンド）の明示**:
   - 抽象的な形容詞や説明文を排し，ファイルパス，Nix オプション名，systemd ユニット名，CLI コマンド，数値などの検証可能トークンを直接記述する．

### 脱 LLM 推敲チェックリスト
- [ ] 文頭・文末に余計な前置きや感想文（「ここでは〜を解説します」「〜が可能になります」等）がないか？
- [ ] 架空の二項対立（「Aであり，Bではない」「単にAだけでなくBでもある」）の否定節が削られ，事実のみが直接記述されているか？
- [ ] 不要な接続詞（さらに，また，このように等）が削られ，文の順序で論理が伝わるようになっているか？
- [ ] 禁止ワード（包括的，堅牢，シームレス，活用，robust, seamless, leverage, delve 等）が含まれていないか？
- [ ] 曖昧な賞賛形容詞を排し，技術的事実・機構・数値が記述されているか？
- [ ] 冗長な述語（〜を行う，〜することが可能である）が直接の動詞に圧縮されているか？
- [ ] 日本語の句読点は `，．` で統一されているか？
- [ ] 英語は簡潔な Plain Technical English（能動態・命令文中心）になっているか？

## 4. 情報の重複排除と一元化

1. **手順・仕様の重複禁止**:
   - 同一の手順（新ホスト追加，SOPS 鍵登録，private flake input のブートストラップ等）を複数の README やスキルに重複して書かない．
   - 手順詳細は `docs/operations/` 配下にまとめ，他のドキュメントからはリンクを張る．
2. **サブディレクトリ README のスリム化**:
   - 各コードディレクトリの README は，当該ディレクトリ固有の仕様・オプション一覧・クイックコマンドに絞る．
   - ハードウェアのチューニングやトラブルシュートは `docs/hardware/` や `docs/troubleshooting/` に委ねる．

## 5. 相互参照のルール

ドキュメント間およびコードとの相互参照を徹底し，読者やエージェントが迷わず関連情報へ到達できるようにする．

- **相対パスのリンク**:
   - `[ネットワーク設計](../../../docs/architecture/network-topology.md)` のように，相対パスでリンクを張る．
- **アンカーリンクの明記**:
   - 特定のセクションを参照する場合は，アンカーを正確に付与する．
- **関連ドキュメント節の設置**:
   - 各ドキュメントの末尾に `## 関連ドキュメント` または `## References` 節を設け，関連する `docs/`，コード，外部資料へのリンクをまとめる．

## 7. ドキュメントレビューと改善

ドキュメントの新規作成や大幅な改修を行った際は，技術的整合性と文章品質の双方を確認する（外部ワーカーへの技術検証委譲やサブエージェントによる文章推敲は `GEMINI.md` および `coding-worker` スキルを参照）．コミット・PR 作成の手順は `dev-workflow` スキルに従う．

### 技術的整合性の検証観点
手順書・設計書に記載された技術仕様，シェルコマンド，systemd ユニット名，Nix 設定値，ネットワーク構成について以下を確認する:
- 記載されたコマンドが実際のホスト環境・NixOS 仕様に合致しているか．
- 参照されているファイルパスやサービス名がリポジトリ内のコードと整合しているか．
- 復旧手順や運用ランブックに手順抜けやエッジケースがないか．

### 文章品質・整合性・コメント（`hush`）の検証観点
ドキュメントの文章，章立て，相互参照，コード内コメントについて以下を確認する:
- **脱 LLM 規則の遵守**: 第 3 節の「LLM 文章脱却チェックリスト＆リライトルール」に従い，前置き・結びの排除，禁止ワードの不使用，冗長述語の圧縮が行われているか．
- **重複の排除と一元化**: 他ドキュメントとの不要な重複がないか，基準となる `docs/` を参照しているか．
- **リンクの正確性**: 相対リンクおよびアンカーが正しく機能しているか（リンク切れがないか）．
- **コメント精査（`hush` 規約）**: コード内コメントが `hush` スキル（`~/.agents/skills/hush/`）に従っているか（自明な解説がなく，名前で意図を表現できているか）．
