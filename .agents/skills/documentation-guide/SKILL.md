# ドキュメント執筆・保守ガイドライン

このリポジトリにおけるドキュメント体系の整合性，鮮度，可読性を維持するための執筆・保守ルールである．なお，ドキュメントやスキルの作成・変更作業におけるワークフロー（ブランチ作成，一時ワークツリー運用，検証・スキップ判断，差分統合，コミット・PR 作成等）は `dev-workflow` スキルに従う．

## 1. ドキュメント体系と責務分離

| 階層 / ディレクトリ | 言語 | 役割・責務 | 含まないもの（委ねる先） |
| :--- | :--- | :--- | :--- |
| **ルート** (`README.md`, `README.ja.md`) | 英 / 日 (同期) | リポジトリ概要，Tech Stack，全体構成，クイックスタート | 詳細な手順や各ホストの深掘り (`docs/`, `hosts/`) |
| **`docs/`** | 日本語 | **Single Source of Truth**．システム横断の設計仕様，運用手順，ハードウェア解説，障害復旧 | コードそのものの実装 |
| **各サブディレクトリ** (`hosts/*/`, `nixos/*/` 等) | 英語 | 当該ディレクトリのコード索引，モジュール一覧，ハードウェア諸元 | 長大な運用手順・システム横断の設計 (`docs/`) |
| **エージェント運用** (`AGENTS.md`, `GEMINI.md`, `TODO.md`) | 日本語 | エージェントの行動規範，ツール運用制約，実装進捗 | システムの詳細な技術仕様 (`docs/`) |
| **`.agents/skills/`** | 日 / 英 | エージェントが実行する作業手順・ノウハウ | システム全体の恒久的なドキュメント (`docs/`) |

## 2. 文体・スタイル規則

### 日本語文書 (`docs/`, `README.ja.md`, `AGENTS.md` 等)
- **句読点**: 必ず `，．` を使用する（全角の読点・句点はコミット時に pre-commit フックで `，．` に自動置換される）．
- **文体**: 技術文書として簡潔かつ論理的な常体（「〜である」「〜する」）を基本とする．
- **自然な日本語**: 機械翻訳調や不自然な主述関係，不必要な重複表現を排し，要点を明確に記述する．
- **箇条書き・表**: 視認性を重視し，比較や属性一覧はテーブル，手順は番号付きリストを活用する．
- **図解**: ネットワーク構成や処理フローは Mermaid ダイアグラムを活用する．

### 英語文書 (`README.md`, サブディレクトリ README)
- **文体**: 簡潔で客観的な技術英語（Imperative mood または叙述）．
- **過度な装飾の排除**: コードブロック，リスト，表を中心とし，冗長な説明文は削る．

### コード内コメント (`hush` 規約)
- 原則として英語で記述する．
- `hush` スキル（`~/.agents/skills/hush/`）に従い，自明な解説やコードの言い換えコメントは書かず，名前で意図を表現する．
- コードのみでは意図を読み取れない場合のみ，背景や理由を1〜2行で記述する．

## 3. 冗長性の排除と Single Source of Truth (SSOT)

1. **手順・仕様の重複禁止**:
   - 同一の手順（例: 新ホスト追加，SOPS 鍵登録，private flake input のブートストラップ等）を複数の README やスキルに重複して書かない．
   - 正本は `docs/operations/` 配下に配置し，他からはそこへのリンクを貼る．
2. **サブディレクトリ README のスリム化**:
   - 各コードディレクトリの README は，そのディレクトリ固有の仕様・オプション一覧・クイックコマンドに絞る．
   - ハードウェアの深いチューニングやトラブルシュートは `docs/hardware/` や `docs/troubleshooting/` に委ねる．

---

## 4. 相互参照（Cross-referencing）ルール

ドキュメント間およびコードとの相互参照を徹底し，読者やエージェントが迷わず関連情報へ到達できるようにする．

- **相対パスのリンク**:
  - `[ネットワーク設計](../../../docs/architecture/network-topology.md)` のように，相対パスでリンクを張る．
- **アンカーリンクの明記**:
  - 特定のセクションを参照する場合は，アンカーを正確に付与する．
- **関連ドキュメント節の設置**:
  - 各ドキュメントの末尾に `## 関連ドキュメント` または `## References` 節を設け，関連する `docs/`，コード，外部資料へのリンクをまとめる．

## 6. 複数ドキュメント改訂時のサブエージェント並列委譲（Fan-out）

大規模な改訂，複数ドキュメントの同時新設・更新，または複数セクションに跨がる大規模な保守を行う場合，親オーケストレーター（Antigravity）は単一のターンで直列に編集するのではなく，**`invoke_subagent` の `Subagents: [...]` 配列を活用して複数のサブエージェントを一括並列起動（Fan-out）**する．

### 並列委譲の分割単位

タスクの特性に応じて，ファイル間またはセクション間でコンフリクトが生じない粒度で分割する．

- **ディレクトリ・領域単位**:
  - サブエージェント A: 運用手順（`docs/operations/`）の改訂
  - サブエージェント B: ハードウェアガイド（`docs/hardware/`）の改訂
  - サブエージェント C: エージェント運用規範（`AGENTS.md`, `GEMINI.md`）の改訂
- **ファイル単位**:
  - 複数ファイルに及ぶ変更（例: `README.md` と `README.ja.md` の対訳同期，特定モジュールの README と仕様書の同時改修）を個別のサブエージェントに排他的に割り当てる．
- **独立セクション・章単位**:
  - 単一の巨大なドキュメントであっても，章やセクションが明確に分かれており，編集範囲が重複しない場合はセクション単位で分割委譲できる（ただし Git マージ時の衝突を避けるため，原則としてファイル単位での分離を推奨）．

### 兄弟ワークツリー運用と一括起動ワークフロー

各サブエージェントが安全かつ独立して編集できるように，兄弟ワークツリーと `invoke_subagent` を組み合わせた並列パイプラインを適用する．

1. **兄弟ワークツリーの一括作成**:
   親オーケストレーターは，タスク名前空間配下にサブエージェント用の兄弟ワークツリーを一括作成する（作成コマンドは `dev-workflow` 参照）．
   ```bash
   git worktree add -b docs/topic-subagent-ops .worktrees/<topic>/subagent-ops origin/main
   git worktree add -b docs/topic-subagent-skills .worktrees/<topic>/subagent-skills origin/main
   ```
2. **`invoke_subagent` による一括並列起動（Fan-out）**:
   親オーケストレーターは1回のツール呼び出しで複数のサブエージェントを配列として起動する．直列に1体ずつ起動して待つことは避ける．
   ```json
   {
     "Subagents": [
       {
         "Role": "Ops Docs Specialist",
         "TypeName": "self",
         "Prompt": "作業ディレクトリ: .worktrees/<topic>/subagent-ops\n担当ファイル: docs/operations/...\n..."
       },
       {
         "Role": "Skills Updater",
         "TypeName": "self",
         "Prompt": "作業ディレクトリ: .worktrees/<topic>/subagent-skills\n担当ファイル: .agents/skills/...\n..."
       }
     ]
   }
   ```
3. **並行編集・推敲**:
   各サブエージェントは割り当てられたワークツリー内で独立して推敲・編集を実施し，本スキルの文体規則（常体，句読点 `，．`，SSOT 遵守）に従ってドキュメントを完成させる．
4. **非同期完了報告と選択的統合**:
   各サブエージェントは作業完了時に `send_message` で親オーケストレーターへ報告する．親オーケストレーターは各兄弟ツリーの差分（`git diff`）を精査し，統合用ワークツリー（`main/`）へ選択的に取り込む（統合手順は `dev-workflow` 参照）．

## 7. ドキュメントレビューと改善

ドキュメントの新規作成や大幅な改修を行った際は，技術的整合性の検証と文章品質の確認の双方を実施する．親オーケストレーター（Antigravity）による外部ワーカーへの技術検証委譲やサブエージェントによる文章推敲の詳細は `GEMINI.md` および `coding-worker` スキルを参照する．また，作業ツリーからの差分統合やコミット・PR 作成の一連の手順は `dev-workflow` スキルに従う．

### 技術的整合性の検証観点
手順書・設計書に記載された技術仕様，シェルコマンド，systemd ユニット名，Nix 設定値，ネットワーク構成について以下を確認する:
- 記載されたコマンドが実際のホスト環境・NixOS 仕様に合致しているか．
- 参照されているファイルパスやサービス名がリポジトリ内のコードと整合しているか．
- 復旧手順や運用ランブックに致命的な手順抜けやエッジケースがないか．

### 文章品質・SSOT 整合性・コメント（`hush`）の検証観点
ドキュメントの文章，章立て，相互参照，コード内コメントについて以下を確認する:
- **自然な日本語表現**: 機械翻訳調を排し，簡潔で論理的な常体となっているか．
- **SSOT 原則の遵守**: 他ドキュメントとの不要な重複がないか，正本（`docs/`）への参照になっているか．
- **リンクの正確性**: 相対リンクおよびアンカーが正しく機能しているか（リンク切れがないか）．
- **コメント精査（`hush` 規約）**: コード内コメントが `hush` ルール（`~/.agents/skills/hush/`）に従っているか（自明なコメントがなく，名前で意図を表現できているか）．なお句読点（`，．`）はコミット時に pre-commit フック（ja-punctuation）が自動置換するため，レビュー観点から除外する．
