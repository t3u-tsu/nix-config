# 2026-03-28: torii-chan デプロイ障害とファイアウォール競合の解決

## 概要
`torii-chan` への艦隊監視ダッシュボード（Prometheus + Grafana）本番デプロイ時に発生した、「静かなるビルド失敗（SSHハング）」と「ブラウザからのアクセス拒否」の2つの深刻なインフラ障害を特定し、恒久対応を行いました。

## 発生した問題と原因特定

### 1. サンドボックスおよび Seccomp BPF エラーによるビルドクラッシュ
- **症状**: `torii-chan` に対するデプロイ（`comin` や `target-host` 経由の `nixos-rebuild`）が、一切のエラーを出さずに沈黙するか、SSH 接続のハングアップを引き起こした。
- **原因**: ユーザーのシリアルコンソール (`picocom`) からの出力により、Orange Pi 等のレガシー / カスタム SBC カーネルが有する「Nix デーモンが要求するカーネル名前空間（User Namespaces）および Seccomp BPF フィルタへの非互換性」が原因で、評価・ビルドプロセスがクラッシュしていることが判明。
- **対策**: `hosts/torii-chan/configuration.nix` の `nix.settings` に対し、`sandbox = false` および `filter-syscalls = false` を明示的に設定し、旧式カーネルでの安全なデプロイを保証した。

### 2. `wg0` インターフェースにおける `lib.mkForce` のアクセス遮断
- **症状**: ビルドフェーズを完全に通過し、サービス (`grafana`, `prometheus`) が `torii-chan` ローカルで起動・稼働したにも関わらず、VPN (WireGuard / `10.0.0.1`) 経由で BrokenPC のブラウザからポート 3000 にアクセスできない（タイムアウトする）。
- **原因**: `hosts/torii-chan/production-security.nix` 内で、NixOS 全体のファイアウォールを上書きする `lib.mkForce` を伴った厳格なルールが存在し、`wg0` インターフェースに対しては「SSH (22) と 8080 以外を完全遮断する」設定になっていた。これにより、`monitoring` モジュールで宣言していたポート開放定義が無効化されていた。
- **対策**: `production-security.nix` の `wg0` 許可リストに、ダッシュボード要求ポートである `3000(Grafana)`, `9090(Prometheus)`, `9100(Node Exporter)` を特例として明示的に追加。

### 3. sudo 権限への特権エスカレーションに伴う SSH 鍵認証の失敗
- **症状**: ローカルでのビルド完了後、リモートへクロージャをコピーする段階で `Permission denied (publickey)` が発生。
- **原因**: ユーザーが `sudo nixos-rebuild` として全体のコマンドを root で実行したため、自身のユーザー領域にバインドされている SSH 秘密鍵やエージェント (`ssh-agent`) が評価できず、リモート側で拒否された。
- **対策**: デプロイコマンドの先頭の `sudo` を外し、一般ユーザー権限で SSH トンネルを確立した上で `--use-remote-sudo --ask-sudo-password` にてリモート先でのみ権限昇格を行うようにデプロイ手順書を修正。

## 結論
SBC のような制約の多いハードウェア上でのネイティブデプロイ、および厳格なセキュリティプロファイル下에서의 新規モジュール追加においては、モジュール側の宣言がハード側のマントルやカーネル制約によって打ち消されるケースを念頭に置いたテスト設計が必須である。
